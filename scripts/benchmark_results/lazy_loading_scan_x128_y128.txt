============================================================
Root cause analysis
============================================================
Bottleneck is h5py per-call overhead (~107 ms/call) for strided hyperslab reads
on contiguous C-order HDF5, NOT disk I/O.  The file is fully in the OS page
cache yet per_pixel still takes ~352s because each handle[:,:,ky,kx] triggers
HDF5 scatter-gather over 16384 elements with 64 KB stride.

scan_row reads Ry=128 contiguous 8 MB blocks — h5py sees a sequential read,
no scatter-gather → 128× fewer h5py calls → ×1283 speedup for the full pass.

slab reads one ky bounding-box hyperslab per chunk.  For sorted BF pixels
(np.where output), chunks span ky_range≈2.2 rows on average → ~19 MB/call.
h5py scatter-gather is bounded by ky_range × Kx elements (not N_bf × 1)
→ ×59 speedup over per_pixel in chunked reconstruction.

============================================================
Auto-detection
============================================================
chunks=None (contiguous HDF5) → auto selects 'slab'
  Rationale: slab balances full-pass speed (×557 vs per_pixel) with chunked
  reconstruction speed (×59) without loading the full file per chunk call.
  scan_row would be ×1283 in full_pass but catastrophic in chunked mode.

Note: the benchmark output above shows "auto-detected mode: scan_row" because
the benchmark ran against an earlier code version.  Commit c3b5b48 corrected
auto-detection for contiguous HDF5 (chunks=None) from scan_row → slab.
